# 播客研报自动化方案

## 目标

每周一、三、五自动检查关注的播客更新，生成一份可核验的中文情报研报，通过 Telegram 发送，并同步保存到 Google Drive 与 Zotero 指定集合中。系统必须保证：

- 播客更新列表完整、可追踪、可去重。
- 每一期播客都有真实 transcript，尽量带时间戳。
- 研报内容只基于 transcript 与节目元数据，不依赖模型猜测。
- PDF 在 Google Drive 备份，并导入 Zotero 指定集合，添加 `unread` 和月份标签，例如 `2605`。

## 推荐总体流程

1. 维护一个 `podcasts.yaml` 关注列表，记录每档播客的 RSS feed、Spotify show URL、语言、分类、优先级。
2. 定时任务在每周一、三、五运行，读取每个 RSS feed 的最新节目。
3. 用本地数据库记录已处理 episode GUID / Spotify episode ID，避免重复总结旧节目。
4. 对新增 episode 拉取节目元数据、shownotes、音频源 URL。
5. transcript 优先级：
   - 官方 transcript：如果 RSS、官网、YouTube、Spotify for Creators 可取得，则优先使用。
   - 第三方字幕：如 YouTube transcript 可用，保留原时间戳。
   - 自动转写：下载 RSS 提供的音频文件，用 Whisper / Deepgram / AssemblyAI 生成带时间戳 transcript。
6. 对每个 episode 生成结构化摘要，要求每条结论回链到 transcript 时间戳。
7. 汇总成研报：Executive Summary、逐条情报、交叉趋势、风险与待核验点。
8. 渲染为横向 PDF，同时保存 Markdown / HTML / transcript JSON，便于未来字幕、翻译项目复用。
9. 上传 Google Drive `1.Spotify情报汇总` 文件夹。
10. 导入 Zotero `1.Spotify情报汇总` 集合，并添加标签：`unread`、当月标签，如 `2605`。
11. 用 Telegram bot 发送摘要消息和 PDF 文件。

## 为什么不用截图作为入口

截图入口最大的问题是“不可验证”：它只能证明 Spotify 页面上看到了一部分更新，不能保证完整，也不能稳定关联到 episode ID。更可靠的入口是 RSS feed 或播客索引服务：

- RSS feed 通常包含完整 episode 列表、发布日期、GUID、音频 URL、shownotes。
- episode GUID 可以用于去重，避免把之前总结过的节目再次放进研报。
- 音频 URL 可用于生成真实 transcript。
- Spotify API 可作为辅助元数据源，但不应作为唯一入口。

## 关键设计

### 更新完整性

每次运行保存一份 `run_manifest.json`：

- 本次检查的播客总数。
- 每档播客的 feed 拉取状态。
- 发现的新 episode 数量。
- 每个 episode 的 GUID、标题、发布时间、来源 URL。
- 已跳过原因：已处理、无音频、发布时间不在窗口内、转写失败等。

研报首页应包含“本次覆盖检查”：

- 检查播客数。
- 新增节目数。
- 成功总结数。
- 转写失败或待人工确认数。

这样你不需要逐条人工核对 Spotify 截图，只需要看 manifest 和异常列表。

### Transcript 策略

Spotify Web API 的 episode endpoint 提供节目元数据，例如标题、描述、发布日期、时长、Spotify 链接等，但官方公开 API 文档没有提供通用 transcript 字段；同时 Spotify API 政策也限制下载 Spotify 内容。因此 transcript 不应依赖 Spotify 页面本身。

推荐路径是：

- 通过 RSS feed 获取音频文件。
- 只在 RSS / 官网授权提供的音频 URL 上转写。
- transcript 存为 `transcripts/{episode_id}.json`，字段包括：
  - `episode_id`
  - `source`
  - `language`
  - `segments`: `start`, `end`, `text`
  - `speaker`，如果 diarization 可用
  - `model`
  - `created_at`

这份 transcript 后续可以直接用于“实时动态字幕”和“翻译”项目。

### 摘要质量控制

每个 episode 总结采用两段式：

1. 单集摘要：只允许引用 transcript 内容，输出核心观点、证据、关键时间戳。
2. 研报整合：跨节目归纳趋势，但每个趋势必须列出支撑 episode 和时间戳。

自动质检：

- 新 episode 数量必须等于成功摘要数 + 失败数。
- 每个摘要至少包含 3 个 transcript 时间戳引用。
- 禁止出现“推测链接格式”。
- 如果 transcript 缺失，研报中只能进入“待转写/待核验”，不能生成事实性总结。
- 如果模型输出了 transcript 中不存在的人名、公司名或数字，标为待核验。

## 需要的账号与密钥

- Telegram bot token 和 chat ID。
- Google Drive API 凭证，用于上传到 `1.Spotify情报汇总`。
- Zotero API key，且需要对目标 library 有写权限。
- 一个转写方案：
  - 本地 Whisper：隐私好、成本低，但慢，长播客对电脑压力较大。
  - Deepgram / AssemblyAI：速度快、时间戳和说话人分离更稳定，但有 API 成本。
  - OpenAI transcription：适合质量优先的统一流程。

## Zotero 导入方式

推荐使用 Zotero Web API 创建一个 top-level item，并把 PDF 作为 attachment 关联到该 item；item 放入目标 collection，tags 设置为：

- `unread`
- `YYMM`，例如 `2605`

如果你更想把 PDF 存在本机 Zotero storage 目录，也可以做，但不如 Web API 稳定，因为 Zotero 本地 storage 目录结构不是给外部脚本直接写入设计的。

## 定时方式

开发阶段先手动运行：

```text
每次运行 -> 输出 manifest -> 输出 PDF -> 发送 Telegram 测试消息
```

稳定后再设为每周一、三、五自动运行。建议运行时间设在北京时间上午，因为欧美播客的前一日更新基本已经沉淀。

## 第一阶段最小可用版本

1. 建立关注播客清单。
2. 自动拉取 RSS，生成“新增 episode 清单”。
3. 自动去重，保存状态数据库。
4. 对新增 episode 生成 transcript。
5. 生成 Markdown + 横向 PDF。
6. Telegram 发送 PDF。

## 第二阶段

1. Google Drive 自动上传。
2. Zotero 自动创建 item / attachment / tags。
3. 增加自动质检报告。
4. 失败重试与成本控制。

## 第三阶段

1. transcript 搜索库。
2. 多语言字幕与翻译。
3. 按主题生成专题研报。
4. 做一个轻量 dashboard，查看每期处理状态。

## 我建议的下一步

先做“更新列表 + transcript + Markdown/PDF 生成”这条主链。只要这条链跑通，你现在最痛的两个点就解决了：不用截图、不会重复总结旧节目；同时 transcript 资产也会开始沉淀。

需要你补充的唯一核心材料是关注播客列表。最理想格式是每行一个：

```text
播客名 | Spotify 链接或 RSS 链接 | 备注/优先级
```
